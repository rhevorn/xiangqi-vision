# 中国象棋 AI 辅助系统

用安卓手机下象棋时，让电脑帮你盯着棋盘：自动认出对方走了哪一步，然后立刻用本地
象棋引擎算出你该怎么走。

手机端不需要装任何东西，电脑上跑一个命令行程序就行。所有计算都在本地完成，
不联网、不调用任何云端服务。

```text
安卓手机 → ADB 截图 → 棋盘差分 → 推断走法 → 规则校验 → 引擎搜索 → 最佳走法
```

## 设计思路

这类工具常见的做法是「截图 → AI 识别 32 枚棋子 → 重建局面」。这条路又慢又脆：
识别错一个子，整盘棋就废了。

这个项目换了个思路：

> **视觉只负责发现变化，象棋规则维护真实状态，引擎专门负责搜索。**

具体来说：

- **不识别棋子**。程序启动时内部棋盘就是标准开局，之后每一帧只比较 90 个交叉点
  的灰度差异，找出「哪两个格子变了」——而不是重新认出所有棋子是什么。
- **视觉只提供候选**。两个变化的格子之间有正反两个方向，两个候选都交给象棋规则
  裁决。规则会否掉绝大多数错误猜测：比如「炮二平五」的反向走法在开局根本不可能
  成立，因为那个位置上没有棋子。
- **认错了也不写进棋盘**。推断不出合法走法时，内部棋盘保持原样，只提示你重新同步。
  宁可漏掉一手，也不能让错误的识别污染状态。

因为只需要差分而不需要识别，整条链路很轻：图像处理只用 Go 标准库，不依赖 OpenCV，
编译出来是一个可以直接分发的静态二进制。

走法规则的正确性不是靠自测，而是与引擎对拍：把 Pikafish 的 `perft` 结果当标准答案，
初始局面深度 1~4 的节点数（44 / 1920 / 79666 / 3290240）逐节点一致。任何一条棋子
规则写错，这个数字都对不上。

## 环境要求

| 组件 | 说明 |
|---|---|
| Go 1.21+ | 编译主程序 |
| Pikafish | 象棋引擎，`make pikafish` 会自动克隆并编译 |
| adb | Android platform-tools，用于抓屏 |
| 安卓手机 | 需要开启 USB 调试 |

macOS / Linux 都可以用。OpenCV **不需要**。

## 构建

```bash
# 克隆并编译 Pikafish（会一并下载 NNUE 权重，首次约需几分钟）
make pikafish

# 编译主程序
make build

# 确认可用
./bin/assistant analyze 炮二平五
```

## 快速开始

```bash
# 1. 确认手机已连上
./bin/assistant devices

# 2. 抓一张截图，确认画面正常
./bin/assistant capture -o shot.png

# 3. 校准棋盘：在浏览器里点两个角点
./bin/assistant calibrate

# 4. 手机上开一局新棋停在开局，然后跑完整链路
./bin/assistant watch
```

### 先不用手机试一下

内置的演示生成器可以合成一段对局的画面，不用连手机就能看到完整效果：

```bash
./bin/assistant simulate                       # 生成一段 10 手开局的画面
./bin/assistant watch -frames testdata/game    # 回放它
```

这一步能跑通，就说明除了抓屏以外的所有环节都是好的。

## 用法

### analyze —— 直接问引擎

不走手机，从命令行构造局面并要建议：

```bash
# 从开局走两步后分析
./bin/assistant analyze 炮二平五 马8进7

# 直接指定局面
./bin/assistant analyze -fen "rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1"

# 想得久一点、多看几个候选
./bin/assistant analyze 炮二平五 -movetime 1000 -multipv 5
```

走法支持两种写法：中文记谱（`炮二平五`、`马8进7`、`前马进七`）和 UCI 坐标（`h2e2`）。

输出形如：

```text
轮到 红方走棋
────────────────────────────────────────
最佳走法  马二进三
局面评分  +0.27
搜索信息  深度 19  用时 400ms  节点 1.7M

候选走法
  1. 马二进三       +0.27
     卒7进1 车一平二 车9平8 车二进六 卒3进1 …
  2. 兵七进一       +0.22
     车9平8 马二进三 炮8平9 …
  3. 马八进七       +0.20
     马2进3 兵三进一 卒3进1 …
```

### calibrate —— 校准棋盘

第一次使用必须校准。程序会抓一张截图并用浏览器打开本地页面：

1. 依次点击棋盘的**左上角交叉点**与**右下角交叉点**——最外侧两条线的交点，
   **不是**棋盘图片的边缘；
2. 页面会实时画出 90 个取样点，确认它们都落在交叉点上；
3. 点「保存」，坐标写进配置，同时输出一张 `debug/calibration.png` 供事后复核。

页面上能看到实时预览，所以点歪了一眼就能发现，还会提示「格子不是正方形」这类
明显错误。

### watch —— 实际对局

```bash
./bin/assistant watch                          # 连真机
./bin/assistant watch -frames testdata/game    # 回放画面序列
./bin/assistant watch -mock                    # 用内置假引擎，只验视觉链路
./bin/assistant watch -board                   # 每步都打印棋盘
```

**重要前提**：程序启动的那一刻，手机画面上必须是标准开局。因为它不识别棋子，
默认「看到的第一帧就是开局」。

运行中可用的按键：

| 键 | 作用 |
|---|---|
| `b` | 打印当前棋盘 |
| `f` | 打印最近一步与当前局面 |
| `r` | 重新同步（回到标准开局） |
| `q` | 退出 |

### 其它命令

| 命令 | 说明 |
|---|---|
| `board` | 打印棋盘，可指定 `-fen` |
| `capture` | 抓一张截图存成 PNG |
| `devices` | 列出已连接的安卓设备 |
| `simulate` | 合成画面序列，用于无手机验证 |

各子命令的完整选项用 `assistant <子命令> -h` 查看。

## 配置文件

默认路径 `configs/config.yaml`，不存在时使用内置默认值，也可以用 `-config` 指定。
`configs/config.example.yaml` 是一份带注释的样例。

```yaml
device:
  adb_path: ""          # 留空则自动探测 PATH 与 Android SDK 常见位置
  adb_serial: ""        # 只有一台设备时可留空

capture:
  fps: 5                # 截图频率。象棋是回合制，2~5 已经足够
  frames_dir: ""        # 用本地画面序列代替真机
  frame_file: ""        # 用固定图片代替真机

board:                  # 由 calibrate 自动写入
  x: 120
  y: 310
  width: 870            # 左上角点到右下角点的横向跨度
  height: 970

vision:
  roi_size: 0           # 取样区域边长，0 表示按格距自动推算（约格距的 45%）
  diff_threshold: 20    # 判定某个格点发生变化的灰度差阈值
  stable_frames: 3      # 判定棋局落定所需的连续静止帧数
  retry_frames: 3       # 推断失败时额外抓取的帧数

engine:
  path: ./bin/pikafish
  threads: 4
  hash_mb: 256
  movetime_ms: 500
  multipv: 3

log:
  level: info           # debug / info / warn / error
  file: ""              # 留空则只输出到终端
```

## 工作原理

```text
抓屏
  ↓
灰度化
  ↓
与上一帧比较 90 个交叉点 ── 还在变（动画/高亮）→ 继续等
  ↓ 连续 N 帧静止
与「上一个稳定帧」比较，找出变化的格点
  ↓
两两组合成候选走法（正反两个方向都在内）
  ↓
交给象棋规则裁决
  ├─ 都不合法 → 重抓几帧重试；仍失败则标记失步，不更新棋盘
  ↓ 唯一合法
更新棋盘 → 导出局面 → 引擎搜索 → 最佳走法
```

几个关键细节：

- **采样区域只取格子中央**（约格距的 45%）。象棋 App 普遍会在格子上叠加「最后一步」
  高亮框、选中框或可走点提示，这些装饰都在格子边缘，取样区避开它们就不会被误判成走子。
- **稳定判定看最大差异，不看平均差异**。走子只影响一两个格子，取平均会被其余 88 个
  静止的格子稀释掉，漏判还在播放的动画。
- **引擎收到完整的对局历史**。发给引擎的是「起始局面 + 全部走法」而不是单个局面快照，
  这样它才能正确处理长将与重复局面。

## 延迟调优

从对方落子到看到建议，延迟由两段构成：

```text
落子 → 确认画面稳定     stable_frames / fps
     → 引擎搜索         movetime_ms
```

默认配置（`fps: 5`、`stable_frames: 3`、`movetime_ms: 500`）大约是 1.1 秒。想更快
可以调其中一项：

| 调整 | 效果 | 代价 |
|---|---|---|
| `fps: 10` | 稳定判定从 600ms 降到 300ms | 抓屏开销翻倍 |
| `stable_frames: 2` | 再省一帧 | 对动画的容忍度下降 |
| `movetime_ms: 350` | 直接省 150ms | 棋力略降（仍有 18 层左右） |

`fps: 10` + `movetime_ms: 350` 大约 550ms，余量比较舒服。

另外 `watch` 默认开启渐进式显示：引擎搜到浅层就先给一个答案，之后不断刷新，所以你
看到第一个结果的时间远早于最终结果。

## 项目结构

```text
cmd/assistant/          命令行入口
internal/
  capture/              ADB 截图、本地图片、画面序列回放
  vision/               校准、90 点取样、帧差分、稳定判定、走法推断
  game/                 棋盘、走法规则、局面序列化、中文记谱
  engine/               UCI 协议客户端与 Mock 引擎
  analyzer/             把引擎结果翻译成中文记谱与展示结构
  overlay/              终端渲染
  app/                  主循环状态机
  config/               配置文件
```

## 排查

**识别不到走子**
先看 `debug/calibration.png` 里 90 个红点是不是都落在交叉点上——校准偏了是最常见的
原因。再看 `watch -v` 日志里的「变化格」一行：正常走子应该恰好有两个格子的差异明显
高于阈值，其余接近 0。

**偶尔认错、频繁失步**
多半是 `diff_threshold` 偏低，把动画或高亮当成了走子。调高阈值，或调大
`stable_frames` 让它多等几帧。每次识别失败都会在 `debug/` 下留一张标注了变化格点的
截图，一看就知道问题出在哪。

**引擎很慢或棋力异常**
检查 `bin/pikafish` 旁边是否有 `pikafish.nnue`。引擎按工作目录查找权重文件，缺失时
它会静默退化成很弱的搜索。

## 已知限制

- **只支持从标准开局跟踪**。程序不识别棋子，所以中途启动、悔棋、重新开局都会导致
  失步；失步后按 `r` 重新同步（回到开局）即可。
- **不做长将判负**。重复局面的历史会传给引擎，但程序本身不裁定长将。
- **不支持自动操作手机**。它只给建议，落子还是你自己来。

后续可以做的方向：完整棋盘识别（这样中途也能接上）、Mac 浮层显示建议、棋谱记录与
复盘。
